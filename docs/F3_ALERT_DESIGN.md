## 0. 왜 다시 설계하나

valley-ds 원안은 "계곡 → 표준유역 → 유역 안 표고 높은 관측소 → 10분 강우 임계 초과 → 푸시" 였다. R1 이 그 첫 고리를 끊었다 — 30개 계곡 중 유역 안 상류 우량계가 실제로 있는 곳은 3~5개다. 관측소는 15 km 안에 얼마든지 있지만 전부 계곡보다 낮은 읍내에 있다(표고 조건을 빼면 30/30). 관측소를 더 찾아도 해결되지 않는 **구조적** 문제라, 관측소 위치가 아니라 **사용자가 필요한 것**에서 다시 시작한다.

원안의 설계 변수(15 km, 중권역, 관측소 존재 여부)는 데이터 쪽 편의였다. 사용자는 km 도 유역 코드도 모른다. 사용자가 아는 것은 "지금 물에서 나와야 하나", "가도 되나", "얼마나 확실한 얘기냐" 다.

## 1. 실사용자가 묻는 것 → 필요한 경계값

### 1.1 사용자 상황 셋

| 상황 | 질문 | 필요한 신호 | 허용 지연 |
| --- | --- | --- | --- |
| **U1 물가에 있다** (가족이 물에 있고 머리 위는 맑음) | 지금 나와야 하나? | 내 계곡 **위쪽**에 지금 비가 오는가, 물이 불기 시작했는가 | 몇 분. 시간 단위 자료는 무용 |

| **U3 계획** (오늘 저녁·내일) | 내일 갈 만한가? | 단기예보, 특보 예비, 최근 경보 이력 | 시간 단위 |

## 2. 신호 계층 — 계곡별로 있는 것만 쓴다

R1 결과에 사용자 경계값을 대면 계곡마다 쓸 수 있는 신호가 다르다. 한 종류에 걸지 않고 **계층**으로 둔다.

| 계층 | 신호 | 갱신 | 30개 중 가능 | 역할 |
| --- | --- | --- | --- | --- |
| **S1 유역 안 고지 우량계** | R1 A등급: 같은 중권역 ∧ ≤ 5 km ∧ 표고차 ≥ 50 m (HRFCO 10분 · AWS 1분) | 1~10분 | **3** (유명산·어비 ← 중미산, 광덕 ← 광덕산 AWS). ≤ 8 km 로 넓히면 5(+지장산·소요산) | 최고 확신. 단계를 직접 올린다 |
| **S2 인접 산지 우량계** | 표고 ≥ 계곡 ∧ ≤ 10 km, **유역 무시**(능선 너머: 백운 ← 광덕산 3.1 km, 가평 북면 ← 포천이동) | 1~10분 | **11** | 옆 유역의 비 = 같은 구름일 확률이 높지만 내 계곡 비는 아니다 → **관심 단계까지만**, S3 가 동의하면 승격 |
| **S3 격자 강수** | 레이더 합성 강수(5분, 1 km 미만) 또는 초단기예보 강수(10분 갱신, 5 km 격자, 6시간) — 유역 폴리곤 평균 | 5~10분 | **30** (형식·활용신청 **확인 필요**, K1 추가) | 관측소가 없는 계곡의 유일한 U1 신호. "추정" 태그 |
| **S4 하류 수위** | 같은 표준유역 하류 수위 관측소(HRFCO 10분) 4단계 + 상승 속도 | 10분 | **20** (4단계 값 있음 18) | **지연 신호**("이미 불었다"). 승격·해제 판정·사후 검증. 리드타임은 음수라 단독 경보는 안 됨 |
| **S5 시군 호우특보** | 기상청 특보(주의보·경보) | 발표 시 | 30 | 하한. U2·U3 의 주 신호 |

**계곡별 확신 등급** = 가진 최고 계층: **관측**(S1) 3/30 · **추정**(S2 또는 S3) 27/30 · **특보만**(S3 미확보 시) 0~27.

## 3. 판정 규칙

사용자에게 보이는 단계는 **셋**을 유지한다(기존 `AlertLevel` = watch/warning/evacuate 그대로). 사람이 취할 행동이 셋뿐이기 때문이다.

| 단계 | 사용자 행동 | 문구 |
| --- | --- | --- |
| `watch` 주의 | 짐을 물가에서 올리고 지켜본다 | "상류에 비 · 지켜보세요" |
| `warning` 경보 | **물에서 나온다** | "상류 비 20 mm · 물에서 나오세요" |
| `evacuate` 대피 | 물가·계곡 바닥을 떠난다 | "수위 급상승 · 물가에서 벗어나세요" |

측정 4단계(관심·주의·경계·심각) → 표시 3단계 매핑: 관심·주의 → `watch`, 경계 → `warning`, 심각 → `evacuate`.

**합성 규칙** — 신호별 단계를 구하고 가장 높은 것을 취한다. 단, 출처별 상한이 있다.

1. S1 강우 단계 → 그대로.
2. S3 유역 평균 강우 단계 → 그대로, `confidence: estimated`.
3. S2 → 최대 `watch`. S3 가 관심 이상이면 S2 단계까지 승격.
4. S4 수위 10분 +10 cm → 최소 `warning`; ≥ 심각(srswl) → `evacuate`. 수위는 단독으로 `watch` 를 만들지 않는다(지연 신호). (F3a: almwl 조건은 여름 내 0회 — 트리거에서 뺀다)
5. S5 호우경보 → 최소 `watch`; 호우경보 ∧ S3 관심 이상 → 최소 `warning`.
6. 해제는 §1.2 규칙(강우 < 관심 30분 ∧ 3h < 20 mm ∧ 수위 하강 60분). 단계 하강은 한 번에 한 칸. 해제 뒤 비가 다시 오면 관심부터 즉시 재발령.
7. 15분 넘게 신호가 없으면 단계 대신 `stale` — 회색 "자료 없음", 마지막 시각 표시.

## 4. 사용자 표면

- **구간 카드**(`SegmentCard`) — 메타 줄 맨 앞에 경보 배지. `swimBanned` 경고와 같은 `live` 톤 계열이되 단계별 3색(주의 호박 · 경보 주홍 · 대피 진홍), 배지 안에 확신 등급 점(●관측 ◐추정 ○특보만). 평시에는 **아무것도 그리지 않는다** — 초록 "안전" 배지는 두지 않는다(stale 과 구분이 안 되고, 없는 확신을 준다).
- **상세 시트 타일**(`ValleyDetailFace` `InfoTile`, 그늘 타일 옆) — 라벨 "상류 강우 · 12분 전 · 추정(레이더)", 값 "최근 1시간 18 mm · 수위 상승 중", 아래 한 줄 고지. 평시 값은 "최근 1시간 0 mm · 수위 관심 아래".
- **지도 배너** — `warning` 이상일 때 상단바 아래 띠(C7 헬스 배너와 같은 자리). SSE 로 갱신.
- **푸시**(구독 계곡, S1 이후) — `warning` 이상. 문구는 단계 문구 + 출처 한 줄("광덕산 관측소 1시간 32 mm").
- **자료 없음** — 회색 타일 "15분 넘게 자료 없음 · 마지막 14:20". 배지는 없음.
- **고지** — "관측소·레이더 기반 추정입니다. 상류가 보이지 않으면 물에서 나오는 것이 우선입니다." (면책 항목과 연결)

## 5. 스키마 변경 제안 (`UpstreamAlert`·`Valley`)

기존 `UpstreamAlert` 는 관측소 1개 전제(`stationCode` required). 격자·복합 판정을 담도록 넓힌다. `AlertLevel` 3단계는 유지.

```ts
// UpstreamAlert 확장(제안)
source: 'gauge' | 'adjacent-gauge' | 'grid' | 'waterlevel' | 'advisory';   // 단계를 결정한 신호
confidence: 'observed' | 'estimated' | 'regional';                          // 사용자에게 보이는 확신 등급
stationCode?: StationCode;            // gauge/adjacent-gauge/waterlevel 일 때
rainfall10mMm?: number; rainfall1hMm?: number; rainfall3hMm?: number;
basinRainMmPerH?: number;             // grid: 유역 평균 강수 강도
waterLevelStage?: 'attention' | 'caution' | 'alert' | 'severe';  // S4 4단계
waterLevelDeltaM?: number;            // 10분 변화
observedAt: IsoDateTime;              // 신호 관측 시각(issuedAt 과 분리 — 지연 표시용)
leadTimeMin?: number;                 // 집수역 도달시간 추정(있을 때)

// Valley 정적 속성(등록 시 산출, R2)
basin: { sbsncd: string; catchmentKm2?: number; leadTimeMin?: number };
alertCapability: 'observed' | 'estimated' | 'regional';  // 그 계곡이 낼 수 있는 최고 확신
```

`verified`(사후 검증)는 유지 — S4 수위가 실제로 올랐는지로 자동 채운다(원안 5번의 "경보 이력 → 임계값 튜닝").

## 6. 커버리지 재정의 — 사용자 경계값 기준

"경보 가능" 을 **"리드타임 ≥ 30분인 U1 신호가 있는 계곡"** 으로 다시 세면:

| 신호 조합 | 30개 중 | 비율 | 의미 |
| --- | --- | --- | --- |
| S1 만 | 3 | 10% | 관측 기반은 여기까지 |
| S1 + S2 | 11 | 37% | 인접 우량계를 관심 단계로 쓰면 |
| S1 + S2 + **S3** | 30 | 100% | **격자가 검증되면** 전 계곡. 품질은 미검증 |
| S4 수위 확인 가능 | 20 | 67% | 승격·해제·사후 검증 |

결론은 R1 과 같다 — 격자 없이는 40% 아래고, **F3 의 생사는 S3(격자 강수) 검증에 달렸다.** 그래서 F3 첫 단계는 UI 가 아니라 F3a 스파이크다.

   - 소요산: AWS 하봉암(2.9 km, +24 m) + 수위 신천교(5.1 km, 4단계) — S1·S4 모두 있는 최적 쌍
   - 광덕계곡: AWS 광덕산(2.7 km, +472 m) + 수위 일광교(8 km)
   - 경반계곡: 상류 우량계 없음 → **S3 격자 vs 수위 가평교(4.3 km)** — 격자가 관측소를 대신할 수 있는지 보는 사례
3. **측정** — 강우 시작 → 수위 상승 시작 지연(분), §1.2 임계값별 오경보·미경보 수(수위 관심 이상 도달을 정답으로).
4. **판정** — 지연이 ≥ 30분인 사례가 2/3 이상이고 격자 vs 수위 상관이 관측소 사례와 같은 부호·순서면 경계값 표를 확정하고 F3b 로. 아니면 리드타임을 낮추거나(경계값 표 갱신) S2 상한을 올린다.

## 9. 의존·순서

- **K1 추가**: 기상청 API허브 레이더/격자 강수 활용신청(F3a 1번에서 항목 확정), 특보 조회.
- **R2**: 계곡별 표준유역 코드(이미 1건 성공) + 저장 방식(국토부 WFS 공공누리 1유형 기본안).

- **F3a**(이 문서 §7) → **F3b**(스키마 §5 + 카드 배지·상세 타일·배너) → **F3c**(구독·푸시).
