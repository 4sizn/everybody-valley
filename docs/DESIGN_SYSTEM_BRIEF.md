# DS1 — 디자인 시스템 재설계 브리프

작성 2026-09-08 (사용자 요청). 담당은 독립 워크트리의 디자인 에이전트다.

## 사용자 요청 (그대로)

> 지금 디자인시스템에 해당되는 내용 즉 컴포넌트 요소가 뒤틀리거나 컨셉에 맞지가 않아보임.
> 디자인 에이전트를 새로 만들어서 독립된 워크트리로, 해당 앱을 분석 및 조사해서 디자인 시스템 및
> 디자인 컴포넌트를 재설계 및 제작해서 사용자에게 검수를 맡아야함. https://seed-design.io/foundations
> 를 학습해서 디자인시스템을 고착화해. 참고만하고 디자인토큰 및 컨셉은 우리 서비스에 맞게 작업
> 잘해놔라. 여기 앱 조건은 색깔이 너무 다채로우면 안된다. 화이트 / 다크테마를 제공하고. 다채롭지 않도록

## 문제를 숫자로

메인 세션 실측(2026-09-08):

- **고유 hex 색 106개** (`packages/map-style/src/*.ts` + `apps/valley-map/src/theme/*.ts` + 앱 `.tsx`).
  가장 색이 많은 파일: `palette.ts` 64개 · `tokens.ts` 46개 · `baseStyle.ts` 13개 · `terrainLayers.ts` 12개.
- **시맨틱 색 상수 묶음 17개**: `FACILITY_COLORS`(9종) · `CROWD_STATUS_COLORS`(3) ·
  `ALERT_LEVEL_COLORS`(3) · `SHADE_AMOUNT_COLORS`(3) · `SHADE_COLORS` · `REPORT_TYPE_COLORS`(6×2테마) ·
  `SEGMENT_CASING_COLORS` · `SEGMENT_LINE_COLOR` · `SEGMENT_UNKNOWN_COLOR` · `WATER_COLORS` ·
  `FACILITY_PIN_STROKE_COLOR` · `LIGHT/DARK_COLORS` · `LIGHT/DARK_MAP_PALETTE` · `LIGHT/DARK_PALETTE`.
- 이 위에 지형 색(`COLOR_RELIEF_STOPS` 50~1100 m 구간별)과 기저 지도 색이 더 있다.

**색이 늘어난 경위** — 기능을 항목별로 붙일 때마다 그 항목이 자기 색 묶음을 하나 더 만들었다.
F5 검토(2026-09-07)에서 이미 "시설 9 + 혼잡 3 + 경보 3 + 그늘 3 + 유형 6 = 24색이 한 화면에서
경쟁한다" 고 짚혔고, 그때는 유형 칩을 6색으로 가기로 결정했다. 사용자의 지금 지적은 그 누적에
대한 것이다 — **개별 결정은 타당했지만 합이 컨셉을 잃었다.**

## 절대 제약 — `/firework` 보존

**이것이 이 작업의 가장 큰 함정이다.**

`apps/valley-map/src/theme/tokens.ts` 의 **다크 토큰은 클론한 데모의 원본 값**이다(파일 주석:
"다크 값을 바꾸면 파리티가 깨진다"). `docs/PARITY.md` 의 측정표와 `test/tokens.parity.test.ts` 가
그 값을 고정한다. `CLAUDE.md` 의 `/firework` 보존 규칙도 같은 것을 요구한다.

**따라서 공유 토큰을 갈아치우는 재설계는 불가하다.** `CLAUDE.md` 의 **"공유 대신 클론"** 규칙
(2026-09-07 사용자 규칙)이 답을 이미 정해 두었다:

> 계곡 화면이 `/firework` 의 어떤 부분과 같은 것을 필요로 하면, 공유하지 말고 클론한다.
> 코드 중복보다 원본 보존이 우선이다.

**→ 계곡 화면은 자기 토큰 세트를 갖는다. festival 은 데모 토큰을 그대로 쓴다.**
새 시스템의 이름·구조는 자유지만, festival 이 읽는 값은 한 개도 바뀌어서는 안 된다.
(이건 새 결정이 아니라 기존 사용자 규칙의 적용이다.)

## 참고 — seed-design.io/foundations

**참고만 한다. 값과 컨셉은 우리 서비스에 맞춘다**(사용자 지시).

실측 확인한 seed 의 뼈대:

- foundations 16항목: Design Token, Color, Typography, Iconography, Elevation, Gradient,
  Inclusive Design, International Design, Layout, Motion, Radius, Spacing, State,
  Voice and Tone, Writing, Feedback.
- **토큰 2계층** — ① **Scale Token**: "Raw value Scale 하나에 이름을 부여한 것"(출력 장치
  세부를 숨기고 플랫폼 불가지론 유지) ② **Semantic Token**: "Scale Token 의 조합으로 디자인
  의도를 표현한 단위". 예시 이름 `fg.brand` · `bg.brand` · `global-gutter`.
- **색은 역할 기반 색(Role Based Color) + 팔레트 색(Palette Color)** 두 층. 역할 기반이 기본이고,
  팔레트 색은 "역할로 표현하기 어려운 예외"에만. 역할을 정의해 두면 테마 전환에 자동 적응한다.

가져올 것은 **이 계층 구조와 "역할이 먼저"라는 태도**다. seed 의 구체적 색값·브랜드색은 가져오지
않는다(당근 브랜드다).

## 이 앱의 컨셉 — 색을 절제해야 하는 실제 이유

계곡 안전·정보 앱이다. 화면의 대부분이 **지도**이고, 지도 위에는 이미 자연색(숲 녹색·물 파랑·
지형 음영·도로)이 깔린다. 그 위에 UI 색을 얹는 구조라 **UI 가 다채로우면 지도가 안 읽힌다.**

그리고 이 앱에는 **색이 뜻을 갖는 자리**가 따로 있다 — 경보(관심·주의·대피)와 물놀이 금지다.
**색을 아껴 두어야 그 자리가 보인다.** 시설 9종·제보 6종처럼 "구분"만 필요한 것에 색을 쓰면
"위험"의 신호가 묻힌다. F5 검토에서 A1(긴급만 색)을 권고한 이유가 이것이었다.

## 산출물

1. **토큰 체계** — Scale → Semantic 2계층. 라이트·다크 두 테마. 역할 이름은 우리 도메인에 맞게
   정한다(seed 이름을 베끼지 않아도 된다). 계곡 전용 세트로 두고 festival 토큰은 건드리지 않는다.
2. **색 감축안** — 106색이 어디로 가는지 표로. 무엇을 역할로 흡수하고, 무엇을 중립(회색 단계)으로
   내리고, 무엇을 **색 없이 아이콘·라벨로** 구분할지. 색을 남기는 자리마다 **왜 여기는 색이어야
   하는지** 한 줄 근거.
3. **컴포넌트 재설계** — 지금 뒤틀려 보이는 것들: 카드(구간·제보) · 배지·칩(경보·그늘·유형·필터) ·
   시트 면 헤더 · 컨트롤 버튼 · 지도 핀 · 티커 · 폼(제보). 각 컴포넌트의 상태(기본·선택·비활성·
   경고)를 정의한다.
4. **검수 페이지** — HTML 파일로 만든다(`docs/design-review/` 또는 `.proof/DS1/review.html`).
   메인 세션이 Artifact 로 게시해 사용자에게 보여준다. **지금 화면 스크린샷(before)과 제안(after)을
   나란히** 놓는다 — 글로만 설명하지 마라(`CLAUDE.md`·기획 승인 규칙).
5. **적용 계획** — 한 PR 로 다 바꾸지 않는다. 무엇을 먼저 바꿀지 순서와 각 단계의 파리티 위험.

## 하지 말 것

- **코드를 대규모로 바꾸지 마라.** 이 작업은 **설계와 검수까지**다. 토큰 파일 신설과 그것을 쓰는
  **예시 1~2개**까지는 허용하되, 앱 전체를 새 토큰으로 옮기는 것은 승인 후 별 항목이다.
- festival 컴포넌트·`tokens.ts` 의 다크 값·`docs/PARITY.md` 를 고치지 마라.
- 지도 스타일의 기저 색(`baseStyle.ts`)을 임의로 바꾸지 마라 — 지도 팔레트는 C2 에서 사용자가
  검수한 결과다(라이트 지도 재색칠). 바꿀 제안은 검수 페이지에 올려 승인을 받는다.
- 색을 늘리는 방향의 제안은 금지다. 순수 결과로 **고유색 수가 줄어야 한다**(숫자로 보고).
