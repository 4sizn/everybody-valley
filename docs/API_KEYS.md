## 3. 약관에서 확인된 것 — 결정에 영향

- **VWorld 영리 이용은 사전 서면 승인**(이용약관 §13⑤·§20③). **데이터 무단 저장 금지**(§19④·⑥) → 정사영상·지적도
  타일을 서버에 캐시하거나 재배포할 수 없다. 결과물에 브이월드 이용 표시 의무(§13⑨). 키는 본인 한정·양도 금지.
  → 운영 전에 **문의 메일 1통이 필요**하다(아래 4절). D4(베이스맵은 openfreemap 유지, VWorld 는 오버레이만)는 이 약관과 맞는다.
- ~~**물놀이관리지역은 WMS 만** 제공한다~~ → **정정(2026-09-06, SD1b 실측)**: data.go.kr 등재는 WMS 뿐이지만 safemap 사이트가 `POST https://www.safemap.go.kr/wtrPlay/getSearchList.json`(폼: `sidoNm`·`sggNm`·`pageIndex`)로 **시군별 목록을 JSON** 으로 준다 — `PLC_NM`(장소)·`MANAGEMENT`(일반/중점/위험지역)·`PLC_TYPE`(하천·계곡…)·`ADRES`·`WATER_DEEP`(최대 수심 m)·`WATER_AVG`(평균)·`X`/`Y`(EPSG:3857), 10건/페이지 + `totalCount`. 키 불필요(Referer 필요). 가평군 32건 확인. 재전송 금지 조항은 그대로이므로 **원본 배포는 하지 않고 계곡 속성으로 인용**한다. WMS·CSV 없음은 여전히 사실. → R4 의 "가장 좋은 공식 시드"는
  그림(WMS)으로만 받을 수 있다. 시드 좌표는 생활안전지도 화면에서 수기 수집하거나, WMS GetFeatureInfo 로 점 단위 조회.
  `swimBanned`·`riskNote` 자동 매칭(R4 2h 추정)은 **재산정 대상**.
- 한강홍수통제소는 출처 표시 조건 자유 이용, 관측소 제원 API 에 위경도·영점표고가 있어 R1 커버리지 계산에 바로 쓴다.

## 5. 키 보관 규약

- 변수 목록과 각 키의 용도·신청처·한도 요약은 저장소 루트 **`.env.example`** 에 있다(값은 비어 있음). 이 파일을 `.env.local` 로 복사해 값을 채운다. `.env*.local` 은 gitignore 되어 있다.
- 키를 받으면 값은 채팅에 붙이지 말고 `.env.local` 에 넣는다. 저장소에는 **어느 키를 받았는지와 한도**만 `docs/TODO.md` 결정 기록에 남긴다.
- S1(서버) 착수 시 `.env.example` 의 이름을 그대로 `server/` 설정으로 옮긴다.
- `ADMIN_TOKEN`(OPS1, 제보 운영 도구)은 외부 API 키가 아니라 이 서버가 스스로 검증하는 값이다 — `openssl rand -base64 32` 로 생성해 `.env.local` 에 넣는다. 비어 있으면 관리자 API(`/api/admin/*`)전체가 404.

## 6. VWorld 개발키 실측 (2026-09-04)

- 서버(curl, Referer 없음)에서 `api.vworld.kr/req/wfs` GetCapabilities·GetFeature 가 두 키 모두 정상 응답 — **도메인 검사는 서버 호출에 걸리지 않는다**(브라우저 Referer 기준). S1 프록시 전제와 맞는다.
- WFS 1.1.0 + `EPSG:4326` 의 `BBOX` 는 **위도,경도 순서**다(경도,위도로 보내면 0건). `EPSG:900913`/`3857` 미터 BBOX 도 된다. 응답 `OUTPUT=application/json` 은 GeoJSON, 좌표는 경도,위도.
- 유역·하천 레이어 이름: `lt_c_wkmbbsn` 대권역 · `lt_c_wkmmbsn` 중권역 · `lt_c_wkmsbsn` 표준권역(표준유역) · `lt_c_wkmstrm` 하천망 · `lp_pa_cbnd_bubun` 연속지적도. 전체 177 레이어.
- **R2 의 point-in-polygon 1건**: 샘플계곡 중류 점(127.2659, 37.8303) → 표준유역 `sbsncd 101802 "퇴계원수위표"`, 중권역 `mbsncd 1018`, 대권역 `bbsncd 10` (1건, 73KB). 같은 2km 상자에서 하천망은 `왕숙천`(지방2급하천, `riv_cd 1024740`) 폴리곤 1건(397KB). 속성 키: `sbsncd sbsnnm bbsncd mbsncd cat_cde cat_nam` / `riv_nm riv_cd riv_level inadm inbsn`.
- 받은 폴리곤은 **저장소에 넣지 않았다**(약관 §19 데이터 저장 금지 — 4절 문의 답신 뒤에 R2 에서 저장 방식 결정).

## 7. 키 검증 실측 (2026-09-04)

- **기상청 API허브**: 키 인증은 통과했지만 `stn_inf.php?inf=AWS` 가 `403 "활용신청이 필요한 API 입니다"` → API허브는 **API 마다 활용신청**이 따로 필요하다. 신청할 것: 지상관측 › 방재기상관측(AWS) › **AWS 매분자료 조회**, 그리고 **지점정보(stn_inf, inf=AWS)**.
- **data.go.kr**: Encoding/Decoding 한 쌍이 서로 일치함(URL 인코딩 관계 확인, 복사 오류 없음). TAGO 도시코드·기상청 초단기실황 호출 모두 `30 SERVICE_KEY_IS_NOT_REGISTERED_ERROR` — 이 코드는 **그 API 에 활용신청이 없을 때**(또는 승인 후 ~1시간 미반영) 나온다. 키 자체의 오류가 아니다.
- **LINK 타입 주의**: 물놀이관리지역(15101866)·하천망(15058825)·표준권역(15056790)·수자원관리도(15057885)는 data.go.kr 에서 **LINK 타입**이다 — `apis.data.go.kr` 로 이 키를 써서 부르는 REST 가 아니라 원 기관 사이트(국가공간정보포털·생활안전지도)로 연결되며 그쪽 절차·키를 따른다. 따라서 이 목록에서 data.go.kr 키로 직접 부르는 REST 는 **TAGO 3종**뿐이다. 키 유효성 확인은 TAGO 버스도착(15098530, 자동승인) 활용신청 뒤 `getCtyCodeList` 로 한다.

## 9. TAGO 정류소·노선 활용신청 (2026-09-07) — 포털 신청 흐름의 함정

N2(막차 역산)에 필요한 두 API 를 개발계정으로 신청해 **자동승인**됐다(마이페이지 승인 3 → 5).

| API | pk | 신청번호 |
| --- | --- | --- |
| 국토교통부_(TAGO)_버스정류소정보 | 15098534 | 0125108060 |
| 국토교통부_(TAGO)_버스노선정보 | 15098529 | 0125108125 |

**신고필증은 필수가 아니다.** 폼의 안내는 "위치정보를 포함한 서비스를 사용하고자 하는 **사업자**"
에게 "**이에 해당하는 사업자인 경우에는**" 첨부하라는 조건부 문구다. 별표(`*`) 필수 항목은
**활용목적과 이용허락범위 동의뿐**이고 첨부파일은 필수가 아니다. 정류소·노선 좌표는 시설의
고정 위치라 개인위치정보가 아니며, 이 앱은 사용자 위치를 서버로 보내지 않는다(`CLAUDE.md`).
반려를 막기 위해 **활용목적 본문에 "왜 신고 대상이 아닌지"를 3개 근거로 적었다** — 심사자가
판단할 근거를 신청서 안에 두는 것이 요점이다.

**흐름의 함정 3개** (다음 신청 때 그대로 겪는다)
1. **폼 URL 을 직접 만들면 실패한다.** `selectDevAcountRequestForm.do?...&publicDataDetailPk=uddi:<id>`
   로 들어가면 폼은 열리지만 제출이 `{result:false, error:"runtime"}` 로 조용히 실패한다.
   실제 `publicDataDetailPk` 에는 **버전 접미어**가 붙는다(`uddi:...-338_202202071347`).
   정식 경로는 `/tcs/dss/redirectDevAcountRequestForm.do?publicDataPk=<pk>&isBusinessApply=undefined`
   다(개인회원은 `isBusinessApply` 가 `undefined` 로 들어간다 — `fn_goOpenAPIRequestForm` 참고).
   이 경로로 들어가면 상세기능·버전이 세션에 세팅된다.
2. **`confirm("신청하시겠습니까?")` 에서 막힌다.** `fn_save()` 는 이 확인창을 거치는데 Orca 내장
   브라우저가 대화상자를 자동 취소해 **버튼을 눌러도 아무 반응이 없다.** 원인 추적 순서는
   `fn_save.toString()` 으로 검증 단계 확인 → `webfilterManager.checkData()` 단독 실행(여기서
   막히면 활용목적 문구 문제) → 확인창.
3. **캡차는 제출 경로에 없다.** 폼에 `captchaCmm` 입력이 있지만 숨겨진 공통 컴포넌트이고
   `fn_save()` 는 캡차를 검사하지 않는다. 처음에 이걸 필수로 잘못 읽었다.

**반영 지연 실측 (2026-09-07)** — 승인 직후부터 1시간 넘게 두 API 모두 `403
SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 였다. 키 문제가 아님을 이렇게 갈랐다: **이미 승인된**
버스도착정보(15098530)의 `ArvlInfoInqireService/getCtyCodeList` 를 같은 키로 부르면
`200 NORMAL SERVICE` 다. 즉 파싱·키·호출 방식은 정상이고 새 승인의 게이트웨이 반영만 남았다.
**새 API 가 403 일 때는 항상 이 방법으로 먼저 가른다** — 승인된 API 한 건을 대조군으로 부른다.

**반영이 하루 단위일 가능성 (2026-09-07 실측)** — 활용신청 현황 페이지에서 세 건 모두
`[승인]`·`계정 개발`·신청일 2026-09-07·만료예정일 2028-09-07 로 확인했다(전체 6건, 보류·반려 0).
그런데 몇 시간이 지나도 세 건 전부 `403 SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 다.

**결정적 정황**: 정상 동작하는 TAGO 3종(버스도착·시외·고속)은 **신청일이 2026-09-04**, 즉 3일
전이다. 같은 계정·같은 키인데 09-04 건은 200, 09-07 건은 403 이다. 따라서 이 게이트웨이의
활용신청 반영은 **즉시가 아니라 하루 이상 걸릴 수 있다**(포털 안내의 "~1시간" 보다 느리다).

**대응** — 신청 당일에 API 가 안 되는 것을 실패로 보지 마라. 판정 순서는 ①활용신청 현황에서
`[승인]` 확인(`/iim/api/selectAcountList.do`) → ②승인이면 **다음 날 다시 호출**. 승인된 다른 API
하나를 대조군으로 함께 불러 키·호출 방식이 정상임을 같이 확인한다.

**Encoding 키를 쿼리에 다시 인코딩하면 403 이다.** `DATA_GO_KR_KEY_ENCODING` 을 `urlencode`
로 다시 감싸면 이중 인코딩되어 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 된다. 코드에서 쿼리
문자열을 조립할 때는 **`DATA_GO_KR_KEY_DECODING` 을 쓰고 인코딩은 한 번만** 한다(실측 확인).

**API 반영 지연** — 승인 직후에도 게이트웨이는 한동안 `403 SERVICE_KEY_IS_NOT_REGISTERED_ERROR`
를 준다(§7 의 같은 코드 해석과 동일, 최대 ~1시간). 승인 여부는 마이페이지 "활용 중 승인" 건수로
판정하고, API 호출로는 판정하지 않는다.

## 11. 2026-09-07 신청 3건이 다음 날에도 403 — 우회 제출이 원인일 가능성

**증상** — TAGO 정류소(15098534)·TAGO 노선(15098529)·기상특보(15000415) 세 건 모두 활용신청
현황에 `[승인]` 인데, 신청 다음 날(2026-09-08)에도 `403 SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 다.
같은 키로 09-04 승인 건(버스도착 등)은 `200 NORMAL SERVICE` — 키·호출 방식은 정상이다.
따라서 §9 에 적은 "하루 단위 반영" 설명으로는 더 이상 설명되지 않는다.

**가장 유력한 원인 — 제출 방식의 차이.**
- 09-04 건: 포털 UI 버튼을 **실제로 클릭**해 신청했다(K1 세션, 확인창은 `orca exec dialog accept`).
- 09-07 건: Orca 내장 브라우저가 `confirm` 을 자동 취소해 버튼이 먹지 않아, `fn_save()` 의 AJAX
  부분만 **직접 호출**했다(`POST /iim/api/saveDevAcountRequest.do`). 응답은 `{result:true, key:…}`.

그런데 원래 핸들러는 성공 뒤 **`fn_uploadFile(json)` 을 부른다**:
```js
success: function(json){ if (json.result === true) { fn_uploadFile(json); } }
```
**이 후속 호출을 하지 않았다.** 신청 레코드는 만들어져 목록에 `[승인]` 으로 보이지만, 게이트웨이
프로비저닝을 마무리하는 단계가 빠졌을 수 있다 — "승인 표시 O · 호출 X" 가 정확히 그 모양이다.

**다음 할 일(사용자 로그인 필요)**
1. 폼 페이지에서 `fn_uploadFile.toString()` 을 읽어 이 함수가 실제로 무엇을 하는지 확인한다
   (단순 첨부 업로드·리다이렉트면 이 가설은 틀렸다).
2. 가설이 맞으면 **포털 UI 로 다시 신청**한다 — 버튼을 눌러 `fn_save()` 를 끝까지 돌리고,
   확인창은 `orca exec --command "dialog accept"` 로 받는다. 기존 `[승인]` 레코드 때문에 중복으로
   막히면 **활용중지 후 재신청**하거나 포털 문의(1566-0025)를 쓴다.
3. 가설이 틀렸으면(=`fn_uploadFile` 이 무관) 포털 문의로 "승인인데 게이트웨이에서 미등록" 을 신고한다.

**교훈 — 폼 제출을 AJAX 로 우회하지 마라.** `confirm` 이 막히면 대화상자를 받는 쪽으로 풀고
(`orca exec dialog accept`), 페이지의 성공 핸들러가 끝까지 돌게 한다. 우회하면 이번처럼 **부분
성공**이 되어 원인 추적에 하루가 든다.
